# ADR-0006. Сессии Django и доступ в админку

**Статус** — принято в v0.2.

Браузерный клиент использует сессии Django с хранением в PostgreSQL. JSON-маршрут входа доступен обычным пользователям каталога. Вход и выход проходят проверку `CsrfViewMiddleware`, включая анонимный POST входа. При успешном входе Django меняет CSRF-секрет, поэтому ответ содержит обновлённый токен. `SessionAuthentication` восстанавливает пользователя для API, а `Membership` определяет доступ к филиалам. В предыдущем варианте Basic Auth передавал пароль при каждом запросе.

Встроенный Django Admin обслуживает доверенных сотрудников по правам моделей Django. Роли `owner` и `viewer` относятся к API каталога. `seed_demo` создаёт обычных пользователей и один набор филиалов в транзакции. Уникальность имени `demo-owner` сериализует создание набора при одновременном запуске. При повторном запуске команда проверяет готовый набор и сообщает его ID. Конфликт с существующей учётной записью завершает команду с ошибкой.

Команда `migrate` добавляет встроенные таблицы `django_session` и `django_admin_log`. На тестовой базе их можно убрать командами `migrate admin zero` и `migrate sessions zero`. Откат удаляет журнал админки и завершает активные сессии. Существующие пользователи и каталог сохраняются.

Browsable API отображает список и карточку филиала через `BrowsableAPIRenderer` на тех же маршрутах. DRF выбирает HTML по `Accept`, а для клиентов с `Accept: */*` по умолчанию отдаёт JSON. Формы `/api-auth/` используют общую сессию Django, проверку CSRF и возвращают пользователя к исходному маршруту. Каталог применяет одинаковый фильтр `Membership` для обоих представлений.
