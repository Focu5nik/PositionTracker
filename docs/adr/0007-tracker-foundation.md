# ADR-0007. База данных и внутренняя аутентификация Tracker

**Статус** — принято в v0.3.

Tracker использует свой пул SQLAlchemy 2 и роль PostgreSQL из `TRACKER_DB_*`. FastAPI владеет пулом в пределах жизненного цикла приложения. Dependency выдаёт отдельную `AsyncSession` для каждого запроса, а сервис определяет границы транзакции. Репозиторий выполняет SQL на переданной сессии.

Для локального `GET /internal/v1/whoami` Tracker проверяет JWT HS256 с фиксированными issuer и audience, сроком действия, субъектом, tenant ID и scopes. Субъект и tenant берутся из подписанного токена. Маршрут доступен только при `TRACKER_ENABLE_DEV_WHOAMI=1` и ключе длиной от 32 байт. Он требует scope `tracker:whoami` и возвращает имя текущей базы как часть диагностики. Выпуск production-токенов будет отдельным решением.

Django предоставляет диагностический GET `/api/v1/tenants/{tenant_id}/tracker/whoami` под тем же dev-флагом. Сессионный пользователь должен иметь `Membership` для tenant из пути. После проверки монолит выпускает JWT на 60 секунд для одного tenant с фиксированным scope `tracker:whoami`. Оба сервиса используют общий dev-ключ. Django отправляет JWT только по настроенному внутреннему адресу Tracker с таймаутом и выключенными перенаправлениями. Ответ браузеру содержит поля диагностики. Локальная подпись в Django позволяет проверить сквозной вызов без сетевого запроса к отдельному издателю.

Обработчик Django проверяет членство и выбирает scopes. `issue_tracker_token()` подписывает переданные ему tenant и scopes. HTTP-клиент принимает готовый JWT, а роутер Tracker проверяет права для конкретного маршрута.

У Tracker своя история Alembic. Ревизия `0001` добавляет запись в служебную `alembic_version`. На существующем томе достаточно применить `upgrade head`. `downgrade base` удаляет строку ревизии и оставляет пустую служебную таблицу. Django-миграции продолжают выполняться отдельно.
